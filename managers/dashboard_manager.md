# spejder.managers.dashboard_manager

**Purpose:**
Generate HTML dashboards for the reporting modules.

**Context:**
Used to summarize and render job offers into presentable HTML files.

**Outcome record (Company Avoid flag):** owned in `workflows/company_catalog.md` — Companies column Avoid between Promote and Action; Yes/No/Cancel bulk-viewed dialog; Promote stays independently toggleable.

**Outcome record — Skills/Companies table headers and column order**

**Problem:**
Skills flag column headers are long and hard to scan, and on Skills and Companies the Action column sits before the property checkboxes (Have/Want/Pass or Promote/Avoid). That breaks a consistent left-to-right pattern of row select, then property flags, then Action beside the name, then the rest of the stats.

**Intent:**
Use short Skills flag headers and the same actionable-column pattern on both tables so operators can scan flags and act on a row without hunting for Action relative to the name.

**Scenario:**
An operator opens the main dashboard Skills or Companies tab and reads the table left to right (headers and cells in the same order).

**Behavior:**
- Wherever the product names these three Skills dashboard columns/flags for operators (table headers, README feature and Skills-tab bullets, companion operator lists, and other chrome that labels the columns), the short names are **Have**, **Want**, and **Pass**. Those short names exist to keep columns narrow. Old long column titles (“I have”, “Want to learn”, “Not for me”) are not kept as alternate names in UI chrome.
- Meanings stay the same. Where a longer clear phrase explains the same meaning better (tooltips, scoring docs, teaching copy), keep or write that long form — do not force every sentence into the three short words.
- Column headers stay short. Checkbox/column tooltips use this exact operator-facing sentence style: Have — “I already have this skill.”; Want — “I want to learn this skill.”; Pass — “This skill is not for me. Score penalty.” Sortability may stay a separate consistent add-on if other sortable headers keep “Click to sort.” Pass’s explainer is not Block. The Pass tooltip above is allowed; the ban is on old titles as names/aliases (e.g. “was Not for me”), not on that Pass wording.
- Skills columns left → right: row select, Have, Want, Pass, Action, Skill, Added, Source, Job share, Learned.
- Companies columns left → right: row select, Promote, Avoid, Action, Company, Added, Jobs, Not viewed, Relevant, Not relevant, Applied, Interview, Stopped, Aliases. (Avoid product behavior owned in `workflows/company_catalog.md`.)
- Only user-visible labels, column order, and tooltips change for the Skills/headers contract. Stored identifiers, APIs, and scoring behavior stay the same unless a separate outcome (e.g. Avoid) changes them. Do not rename DB, API, or profile fields unless a user-visible string requires it.
- This record replaces the prior Skills/Companies table layout and label contract. Use-case tests assert the new headers Have / Want / Pass and the new cell order only; they are not required to assert that old labels are absent.
- Failure that matters: a user-facing place that names these three columns still uses the old long titles as chrome names; Pass’s tooltip reads like Block or uses an old title as a name/alias (e.g. “was Not for me”); Have / Want / Pass hints diverge from the locked sentences above; or Action still appears before the property checkboxes / Promote / Avoid so the two tables stay inconsistent.

**Outcome record — Skills/Companies checkbox column widths**

**Problem:**
On the Skills and Companies tables, columns that hold checkboxes still take more horizontal space than they need. Shortened headers already free some room, but padding and column growth keep that space from going to names and stats.

**Intent:**
Make every checkbox column as narrow as practical so name and stats columns get the freed width, without hurting readability of the short headers or the ability to click the checkboxes.

**Scenario:**
An operator opens the main dashboard Skills or Companies tab and scans the table, using the checkbox columns and reading skill or company names and stats in the same viewport.

**Behavior:**
- On Skills, every column that contains a checkbox is minimal width: row select, Have, Want, and Pass.
- On Companies, every column that contains a checkbox is minimal width: row select, Promote, and Avoid.
- Action (icon buttons) is not a checkbox column for this contract. Keeping it compact is fine when it falls out naturally; it is not required by this outcome.
- Checkbox columns are content-sized and visually tight: they do not grow with the table’s leftover space, and header text does not wrap. Width for a sortable checkbox column is the short header label plus the existing sort chrome (indicators stay visible — do not hide them to shrink the column), with no leftover stretch beyond that content.
- Checkboxes stay easy to click even when the column is narrow. Prefer padding or hit area on the control itself, or a tight cell that still centers a usable checkbox — not empty column stretch to invent click room.
- Have, Want, Pass, Promote, and Avoid header text stays fully visible — not truncated, not hidden. Headers stay horizontal always; never rotate them (no escape hatch).
- Name and stats columns absorb the remaining horizontal space (improve existing table layout habits so the freed width lands there).
- Sticky table headers and the existing Skills/Companies scroll panes keep working; this polish must not introduce dual-scroll regressions.
- Prefer presentation-only changes (styles, and HTML class hooks only if styles alone cannot target the columns). No change to flag meanings, APIs, scoring, or the headers/order contract above. Leave any unfinished Company Avoid work intact — this is additive layout polish.
- Failure that matters: a checkbox column still stretches with leftover table space; headers wrap or grow the column beyond label-plus-sort-chrome; sort indicators on these columns are hidden to force narrowness; checkboxes are hard to click because the column was squeezed without usable control hit area; Have/Want/Pass/Promote/Avoid labels are truncated, hidden, or rotated; name/stats columns do not gain the freed space; sticky headers or scroll panes break into dual scroll; or Action is treated as in-scope checkbox-width work beyond optional natural compactness.

**Outcome record — Skills/Companies checkbox column header centering**

**Problem:**
On the Skills and Companies tables, checkbox columns are already narrow and their body cells sit centered, but the header-cell contents stay left-aligned. That misaligns the select-all control or short flag labels with the checkboxes below and makes the tight checkbox strip look uneven.

**Intent:**
Center header-cell contents on every checkbox column (select-all control on the select column; short label with existing sort chrome on flag columns) so each header sits over its checkboxes, without changing how Action or name/stats columns are aligned.

**Scenario:**
An operator opens the main dashboard Skills or Companies tab and reads the checkbox-column headers above the flag and select controls.

**Behavior:**
- On Skills and Companies, center the **header-cell contents** of every checkbox column (not “title text” alone).
- Skills: select + Have + Want + Pass. Companies: select + Promote + Avoid.
- For the **select** column, that means centering the select-all checkbox in the header cell (there is no title string).
- For flag columns, center the short label (horizontal, never rotate). Sort indicators stay available, but on these columns the inactive indicator must not reserve layout width (otherwise Have/Want/Pass or Promote/Avoid look left-shifted under centered header alignment); active arrows may paint without shifting the label’s center.
- Checkbox **body cells** in those columns remain centered as already required by the checkbox-width contract — this outcome does not invent a second cell-centering story; it only ensures header contents share the same center line.
- Action and name/stats columns keep existing alignment (Action centering is a separate later outcome).
- Presentation-only; no API/flag/order/width-rule meaning changes beyond adding text-align (or equivalent) for these header cells.
- Failure that matters: checkbox-column header contents still left-aligned; select-all header checkbox left-biased; Action/name/stats recentered as collateral; sort indicators hard to read or hidden; headers rotated.

**Outcome record — Skills/Companies Action column header centering**

**Problem:**
On Skills and Companies, the Action column title can sit left-aligned while the row icon buttons sit under a different visual center, so “Action” does not line up with the controls the way centered checkbox headers now line up with their checkboxes.

**Intent:**
Center the Action header over the Action controls on both tabs, with Action body cells sharing the same center line; leave name/stats alignment alone. Checkbox-column centering (including zero-width inactive sort chrome on flag headers) stays as already locked — this outcome only extends centering to Action.

**Scenario:**
An operator opens the main dashboard Skills or Companies tab and reads the Action column header above the row icon buttons.

**Behavior:**
- Center the Action **header** text on Skills and Companies (`.skills-action` / `.companies-action` or equivalent).
- Center Action **body** cells as well so header and icon buttons share one center line (required, not optional).
- Do not change name/stats column alignment.
- Do not reopen or weaken the locked checkbox-column centering / sort-indicator layout fix; additive CSS only for Action.
- Presentation-only; no API/order/flag changes.
- Failure that matters: Action header still left-aligned; Action icons clearly off-center under a centered Action title; name/stats recentered as collateral; or checkbox-column centering regressions.
