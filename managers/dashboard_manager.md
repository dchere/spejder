# spejder.managers.dashboard_manager

**Purpose:**
Generate HTML dashboards for the reporting modules.

**Context:**
Used to summarize and render job offers into presentable HTML files.

**Submodules:**
- `dashboard_templates.py` — shared Jinja2 environment; `load_dashboard_card_corners_css()` reads canonical rules from `templates/partials/dashboard_card_corners.css`; the same rules are inlined in `dashboard.html` and `company_dashboard.html` `<style>` blocks (plain CSS for editor linters; keep partial and templates in sync); `test_inlined_corner_css_matches_partial` enforces whitespace-normalized equality between partial and inlined blocks in both templates
- `dashboard_cards.py` — job card HTML (`_build_job_cards` for main/company dashboards; `_render_html_from_items` for simple report cards without applied-date overlays); class constants `RELEVANCE_SCORE_CLASS`, `APPLIED_DATE_CLASS` (+ title attrs); `card_panel` arg controls Applied / Interview / Stopped controls and company feedback UI; applied cards include optional cover-letter checkbox + Save flow (full-width textarea matching manual description input); applied/interview/stopped cards show `<span class="applied-date">Applied: YYYY-MM-DD</span>` from `applied_at` when set (absolute bottom-right on the card, styled like relevance score); when the applied-date span is rendered, the card `<article>` also gets `has-applied-date` for padding rules; shared corner CSS in `templates/partials/dashboard_card_corners.css` (inlined into both dashboard templates): feedback padding `7.5rem` right / `1.5rem` bottom when apply date present (via `:has(.applied-date)` and `.has-applied-date` fallback); stopped cards add `1.25rem` bottom margin on `.company-feedback-input`; applied date text appears only after a report rebuild (not updated live on apply); card UI updates come from background report rebuild, not client-side collapse on save; non-empty `company_feedback` sets `data-company-feedback` on the card article
- `dashboard_sorting.py` — unviewed/score and applied list ordering; applied sort uses completion rule: incomplete manual description or pending cover letter → top, else score; when those keys tie, `applied_at` DESC (newer first; empty/missing last) — second layer after DB `(applied_at IS NULL), applied_at DESC, updated_at DESC`
- `dashboard_manager.py` — facade for company and main dashboard renderers; splits applied-stage items into three tabs: Applied (plain applied), Interview (`on_interview=1`), Stopped (`interview_stopped=1`); Skills tab: sortable columns (default **Added** newest first, `aria-sort` on active header, keyboard Enter/Space on headers), **Added** column between Skill and Source (`YYYY-MM-DD` from `skill_patterns.created_at`; profile-only skills show `—` with tooltip and `data-sort-added-at="0000"` via `SKILLS_EMPTY_ADDED_AT_SORT` so client ASC/DESC both sort profile-only last), header/cell tooltips, **Job share** (% of jobs with extracted skills), **Learned** (`skill_patterns.occurrences`), **Want to learn** checkbox column; checkbox toggles refresh row sort data client-side; passes `skills_empty_added_at_sort` into the Jinja context so `dashboard.html` embeds the same sentinel for client-side `compareRows` (Python tests assert the wiring; client `compareRows` behavior is intentionally not covered — no JS test runner in the repo; test boundary); main dashboard toolbar: Portrait icon plus `.toolbar-action-group` wrappers (regenerate btn+status, sync btn+status); `.regenerate-status` and `.sync-inbox-status` truncate long messages with ellipsis (`max-width: 14rem`); **Portrait** panel (toolbar icon `#btn-portrait`, not a mode tab): embeds committed text from `default_portrait_path` via `embed_portrait_for_textarea` (textarea-safe, not HTML-escaped); passes `has_portrait` for empty-state hint; live edits via `/api/portrait*` when the server is running
